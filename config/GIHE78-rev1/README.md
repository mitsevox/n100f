# GIHE78 revision 1

USA release, disc revision 1. The original is `orig/GIHE78-rev1/sys/main.dol`, 2,032,480 bytes, entry point `0x80016A00`, SHA-1 `cc84bc42b1054b572b5bb65968cf80b71ff41d0b`. The owner supplied it privately; its hash was checked before use. The default target remains `GIHE78-rev0`.

## Initial relink

The initial map was generated by decomp-toolkit v1.8.3 (`e4219e7644fb7b96d920d5bc3d1d950f5569dcaf`) with `tools/patches/dtk-v1.8.3-rom-copy-info.patch`. All units are auto-generated; no source boundaries are claimed. Shared source and revision 0's maps were not copied into this map. At that point no source unit linked on revision 1: every matching declaration named revision 0 only, and revision 1's report omitted the zero-valued `complete_code` and `complete_data` measures.

The following configuration inputs were copied from revision 0, each recorded in `evidence.tsv`. The relink was not tested with either input omitted:

- `mw_comment_version: 10`.
- An identical copy of `ldscript.tpl`, with the debugger stack at `_stack_addr + 0x1000`.

The relink also used the project's existing patched toolkit and entry-point handling in `tools/project.py`.

The sibling's `extract` entry was omitted from the initial map, which does not name `CardData`. Compiler profiles have not been established for revision 1 by source matching.

The first relink failed its executable hash. The owner approved one symbol-name correction: the entry routine at `0x80016A00` has one `bl`, at `0x80016A48`, to the `.init` function at `0x80005304` (size `0x138`, exclusive end `0x8000543C`). That symbol is named `__start` after revision 0's startup function (itself an inferred name on revision 0), with origin `related`. Every other function retains its toolkit-supplied name. Besides neutral toolkit labels, dtk's built-in signatures supplied about 35 names (`GXInit`, `__GXInitGX`, the gTRK vectors and others), covered by the signature row in `evidence.tsv`. As described in revision 0's Baseline notes, mwld places `_rom_copy_info` and `_bss_init_info` in the section of the global `__start`; the name-only change produced a byte-identical relink. The relink proves the bytes, not the name. This proposed name requires independent accuracy review.

To regenerate the initial toolkit map, remove `symbols.txt` and `splits.txt` locally and configure/build with the patched toolkit and the verified original. Also remove the `extract` entry from `config.yml` for that split, because the initial map does not yet name `CardData`, and restore it afterwards. Before expecting a byte-identical relink, reapply the documented name-only change from `fn_80005304` to `__start`, retaining the function's other metadata. Regeneration does not recover a source map or establish original names.

## Ported symbols and units

`symbols.txt` and `splits.txt` are `tools/port_symbols.py GIHE78-rev0 GIHE78-rev1 --write` applied to the initial toolkit map. The tool pairs revision 0's symbols with this revision's, and writes a pair only when the contents are the same apart from relocations: instructions equal once branch targets, small-data offsets and `lis` pairs that form an address are masked (a `lis` that forms a constant stays compared), and data bytes equal outside address words. Uninitialized data has no bytes, so a .bss symbol counts as the same only when every reference into it from paired code or mapped data shifts with it. A unit is carried over only when each of its section ranges has the same length here, every symbol in it maps with the same shift and the same contents, and, for .bss, every reference into the range shifts with it. The two tool rows in `evidence.tsv` state what that claims: a written name or range carries only the claim its revision 0 evidence row records.

At the time of the port (revision 0 at main 01dc49a): 4,509 of 4,745 functions and 6,599 of 6,719 other symbols written. 175 further functions and one .bss object pair by position alone and are not written, because the tool could not show their contents equal; that is not proof they differ. 313 of 400 units are carried over, and 87 are left out for one of three reasons. A range has another length here, so code or data changed: 42 RenderWare units, the AX (AXAlloc, AXAux, AXCL, AXVPB), CARDMount, EXIBios, GX (GXAttr, GXFifo, GXGeometry, GXInit, GXMisc, GXTexture) and OS (OS, OSAlarm, OSInterrupt) SDK units, and the game units iDebug, iFile, iFMV, iFont, iSystem, iMix, iSnd, xFont, xpkrsvc, xsavegame, xstransvc, zMain, zMenu and zSaveLoad. The lengths agree but the tool could not show the contents equal: 6 RenderWare units, dvd, GXDisplayList and zScene. A range edge does not map, though the symbols the tool did map are the same: dvdlow, SISamplingRate, iTime and Bink's binkacd, expand, popmal and fft. `python3 tools/port_symbols.py GIHE78-rev0 GIHE78-rev1 --report <file>` lists every symbol and unit with the reason.

The carried units compile from the shared source and are measured here. A carried unit links here when its declaration names this target, `MatchingFor("GIHE78-rev0", "GIHE78-rev1")`, which is given to a unit Matching on revision 0 whose references all resolve to names this map defines; the others stay `MatchingFor("GIHE78-rev0")`. `python3 tools/link_candidates.py GIHE78-rev0 GIHE78-rev1` lists the units that qualify and why each other unit does not, and `--write` widens their declarations; a build of this target then decides, and a unit that fails it stays revision 0 only. To regenerate after revision 0's map changes, restore the initial toolkit map (above), reapply `__start`, run the tool with `--write`, rename `fn_80169EAC` to `RwFrameCreate` (a name-only change the tool cannot make, because revision 1 moved part of the body into the function before it; see `evidence.tsv`), then build this target once so the toolkit's signature names settle in `symbols.txt` (it names functions in the units left out, such as `OSDefaultExceptionHandler`), and commit that settled map. On the committed map, a second run of the tool and a second build each change nothing. The `CardData` extract is copied from revision 0 because the carried CARD units include it.

## Validation

With the pinned native tools and patched toolkit:

```sh
python3 configure.py --version GIHE78-rev1 --dtk /path/to/patched/dtk
ninja -f build/GIHE78-rev1/build.ninja
ninja -f build/GIHE78-rev1/build.ninja progress build/GIHE78-rev1/report.json
```

The executable check reports `build/GIHE78-rev1/main.dol: OK`. With the ported units, the report measures 2,723 of 4,790 functions (626,432 of 1,607,348 code bytes) matching the shared source, and 179 of 494 units linked (243,680 code bytes, 15.16%). Initial measurement totals, before the port, were 1,599,360 code bytes, 955,052 data bytes and 4,792 functions in 20 auto-generated units, with zero linked or matched bytes. These are this target's own measurements. Empty category percentages do not indicate recovered source. CI, independent review, owner merge and publication are separate gates.
